1.개요 · v2 목적

v1(현행)은 자연어를 받아 gate가 act/answer 이분으로 분기하고, 곧장 plan이 스텝을 만들어 실행한다. 동작은 하지만 — 의도 파악이 불안정하고(잘못된 분기·대상 혼동), 실행이 끝난 뒤 "계획대로·의도대로 됐는지"를 판정하는 단계가 없다. v2는 이 두 가지를 정조준한다: 의도를 1급 산출물로 만들고, 실행 결과를 계획·의도와 대조하는 검증 노드를 추가한 뒤, 그 품질을 테스트로 측정한다. 그리고 결정적으로 — v2의 이 정확도는 자율 개발 루프로 만든다: 측정값(eval 오라클)을 유일한 잣대 삼아 계획 → 구현 → 검증을 AI가 스스로 반복하며 agent/v2/ 코드를 수렴시킨다(§10 로드맵 · §12~15 방법).

1.2 v2의 세 기둥

① 의도 분석 (analyze)
  • gate의 1비트를 IntentSpec 구조로 대체·확장
  • 의도를 목표(goals) 단위로 분해 — 각 목표가 곧 검증 단위
  • 대상 범위(erd/db/concept)·제약·모호성을 명시
  • 모호하면 clarify — 추측 대신 되묻기
② 계획 수립 (plan, 목표 연결)
  • 각 스텝을 goal_id에 연결 + expectation(성공조건) 부여
  • 계획이 어느 목표에 기여하는지 추적 가능
  • 목표 미커버·과잉 스텝을 계획 단계부터 점검
③ 계획 준수 검증 (verify)
  • 실행 후 Verdict 산출: 목표 충족 · 스텝 준수 · 누락 · 과잉
  • 준수율(score)로 정량화 → respond/replan 분기
  • SSE verdict 이벤트로 테스터에게 그대로 노출
④ 검증 오라클 + 자율 개발 루프 (how)
  • 픽스처 기반 오프라인 채점(/agent/v2/eval) — 의도·계획 정확도를 수치화
  • 이 점수를 잣대 삼아 AI가 계획→구현→검증을 자기반복하며 v2를 수렴(§12~15)
  • v1↔v2 A/B · 회귀 감지 · 골든/홀드아웃으로 과적합 차단

2.v1 → v2 변경 매핑

v2는 v1 그래프의 형태를 유지한 채 노드 하나를 교체(gate→analyze)하고 하나를 추가(verify)한다. 나머지(fetch_tools·approve·exec_proxy·execute·respond·interrupt/resume·드래프트 커밋)는 그대로 재사용한다.

v1 (현행)v2 (계획)
gate → RouteDecision{act|answer}analyze → IntentSpec{kind, goals[], constraints[], ambiguities[]} (kind: answer/act/mixed/clarify)
plan → Step{id, tool, args}plan → StepV2{id, tool, args, goal_id, expectation} (IntentSpec.goals 소비)
replan = 남은 스텝 유무 + 느슨한 자기평가verify 노드 신설 → Verdict{adherence, goals[], missing, extra, score} → 그 뒤 replan 재사용
SSE: meta·token·interrupt·done·error+ intent · plan · verdict (관측 이벤트 추가, 기존 이벤트 불변)
라우터 /agent (routers/agent.py)/agent/v2 (routers/v2/agent.py) — 병렬, v1 불변·가드 등록(§9.1)
품질 측정 없음/agent/v2/eval + fixtures.jsonl + 스코어카드 (의도·계획 정확도)
프론트: agent_panel.js 단일 경로별도 js/agent_v2/* (자체 패널·클라이언트·관측 렌더) — v1 프론트 불변
개발 방식: 사람이 프롬프트를 손으로 고치며 추측자율 개발 루프 — eval 오라클 점수를 잣대로 계획→구현→검증 자기반복(§12~15). v1 무손상(§9.1)·픽스처 무변조를 하드 게이트로 강제

3.v2 아키텍처

3.1 그래프 토폴로지

그림 1 — v2 토폴로지. analyze(의도 구조화)와 verify(준수 검증)가 신규/교체 노드. clarify는 모호 시 즉시 사용자에게 되묻고, verify는 실행 결과를 계획·의도와 대조해 pass/partial/fail로 분기한다. 회색 경로(fetch_tools·approve·exec_proxy·execute·replan·respond)는 v1 재사용.
그림 2 — v2의 핵심 3노드와 관측 이벤트. analyze는 intent, plan은 plan, verify는 verdict SSE 이벤트를 흘려보내 — 테스터가 "무엇을 이해했고 / 어떻게 계획했고 / 계획대로 됐는지"를 단계별로 관측한다.

3.2 상태 확장 (AgentStateV2)

v1 AgentState에 의도·검증 필드만 더한다. 기존 필드(messages·erd_context·plan·approved·tool_catalog·past_steps·replan_*)는 의미·리듀서 그대로.

class AgentStateV2(AgentState):           # v1 상태를 상속·확장
    intent:   Optional[dict]              # IntentSpec — analyze 산출 (검증 기준)
    verdict:  Optional[dict]              # Verdict — verify 산출 (준수 리포트)
    # plan[*] 가 v2에선 goal_id·expectation 을 동반 (StepV2)

4.의도 분석 — analyze 노드

v1 gate(act/answer 1비트)를 대체한다. 경량 모델(get_fast_llm)에 ERD 요약·역량 목록을 주고 with_structured_output(IntentSpec)로 구조화된 의도를 받는다. 핵심은 목표 분해다 — 이후 모든 단계가 이 goals를 기준 삼는다. 

class Goal(BaseModel):
    id:           str                                  # g1, g2 … (스텝이 참조)
    description:  str                                  # "회원 테이블 생성"
    action:       Literal["read","create","update","delete","layout","sql","explain"]
    target_scope: Literal["erd","db","concept"]      # 다이어그램 / 운영DB / 일반지식
    target_ref:   str = ""                          # 대상 테이블·컬럼 식별

class IntentSpec(BaseModel):
    kind:        Literal["answer","act","mixed","clarify"]
    summary:     str                                   # 한 줄 의도 요약
    goals:       list[Goal] = []                     # 분해된 목표 = 검증 단위
    constraints: list[str] = []                      # "30자로", "PK 필수" 등 제약
    ambiguities: list[str] = []                      # 모호한 점 (있으면 kind=clarify)
    confidence:  float = 1.0
kind분기의미
answer→ answer → END상태 변경 불필요 (개념·조회성) — v1과 동일 경로
act / mixed→ fetch_tools → plan도구 실행 필요. mixed는 읽기+쓰기 혼합 (v1이 뭉개던 케이스)
clarify→ respond(질문) → END모호성 존재 → 추측 대신 사용자에게 되묻고 종료. ambiguities를 질문으로 변환
왜 의도를 구조화하면 정확도가 오르나
  • 대상 분리: target_scope(erd/db)를 의도 단계에서 결정 → plan 프롬프트의 거대한 "ERD vs 운영DB" 규칙 벽 제거, 혼동 감소.
  • 목표 단위: "회원·주문 만들고 연결" → goals=[g1,g2,g3]로 분해 → plan이 각 목표만 충실히 스텝화.
  • 모호성 게이트: "그거 지워"처럼 target_ref가 비면 clarify → 잘못된 삭제 방지 (보수성).
  • 검증 가능: goals가 곧 verify의 채점 항목 → "의도대로 됐나"를 항목별로 판정.

5.계획 수립 — 목표 연결 plan

v1 plan을 확장한다. 입력이 raw 질의가 아니라 IntentSpec.goals이며, 각 스텝은 어느 목표에 기여하는지(goal_id)와 성공조건(expectation)을 명시한다. (설계서 §6.4가 예고한 expectation 필드를 v2에서 실제 구현.)

class StepV2(Step):                  # v1 Step{id,tool,args} 확장
    goal_id:     str                    # 이 스텝이 기여하는 IntentSpec.goal
    expectation: str = ""             # 성공조건(postcondition) — verify가 대조
계획 단계 점검내용
목표 커버리지모든 goal이 ≥1개 스텝으로 커버되는가 (미커버 목표는 계획 결함)
과잉 방지어느 goal_id에도 속하지 않는 스텝은 제거 (계획 단계 환각 차단)
카탈로그 필터v1 그대로 — tool_catalog(클라) + PROXY_TOOL_CATALOG 밖 툴 제거
의존 순서v1 그대로 — 엔티티 생성 → 관계 → 정렬

6.계획 준수 검증 — verify 노드

v2의 심장. execute 직후, 실행 결과(past_steps)를 계획(plan의 expectation)과 의도(IntentSpec.goals)에 대조해 "계획대로·의도대로 됐는가"를 구조적으로 판정한다. v1 replan의 느슨한 자기평가를 명시적 채점으로 바꾼다.

검증 항목 (4종)

항목판정
목표 충족 (goal)각 IntentSpec.goal마다, 그 goal에 연결된 스텝들의 실제 결과가 목표를 달성했는가 (fulfilled + evidence)
스텝 준수 (step)실행된 각 스텝의 결과가 expectation(성공조건)을 만족하는가 (구조 검증 + LLM 대조)
누락 (missing)계획에 있었으나 실행되지 않은 스텝 · 어느 스텝도 커버하지 않은 목표
과잉 (extra)계획·목표에 없는데 실행된 행동 (의도 이탈 — 가장 위험한 신호)
class GoalVerdict(BaseModel):
    goal_id:   str
    fulfilled: bool
    evidence:  str = ""                # 어떤 스텝/결과가 이 목표를 충족했나

class Verdict(BaseModel):
    adherence: Literal["pass","partial","fail"]
    goals:     list[GoalVerdict] = []
    missing:   list[str] = []           # 누락 목표/스텝
    extra:     list[str] = []           # 계획 밖 실행 (의도 이탈)
    score:     float = 0.0             # 준수율 = 충족 목표수 / 전체 목표수
    next:      Literal["respond","replan","escalate"]
    note:      str = ""

6.1 Verdict 분기

그림 3 — verify의 3분기. pass는 곧장 커밋, partial은 기존 replan을 재사용해 보정 스텝을 받아 execute로 되돌리고, fail(특히 extra≠∅ 의도 이탈)은 안전하게 보고/에스컬레이트한다. replan_count 상한은 v1 그대로 무한 루프를 막는다.
replan과의 관계 — 교체가 아니라 전치(前置)
v2는 replan을 없애지 않는다. verify가 구조적 판정을 먼저 내고(목표·스텝·누락·과잉), 보정이 필요할 때만(partial) 기존 replan이 다음 스텝을 생성한다. 즉 verify=판정, replan=재계획으로 역할을 분리한다. 이로써 v1의 "남은 스텝 있으면 continue"식 암묵 판정이 명시적 채점 → 재계획으로 바뀐다.

7.검증 하네스 — 품질 측정 + 자율 루프의 오라클

"계획대로 실행하는지 테스트한다"는 목적을 두 계층으로 구현한다. 런타임 verify(매 턴 자기검증)는 §6에서 다뤘고, 여기서는 오프라인 채점 하네스를 정의한다 — 프롬프트·모델을 바꿀 때 의도·계획 품질이 좋아졌는지 회귀했는지를 수치로 답한다.

🎯 이 하네스는 동시에 자율 개발 루프의 오라클이다 (§12~15)
같은 채점기가 두 역할을 한다 — (사람용) v1↔v2 A/B 스코어카드, (루프용) AI가 향하는 손잡이. 자율 루프(§12)는 매 라운드 이 채점 점수로 "진전/회귀"를 판정하고 정지 시점을 안다. 오라클 없이는 루프가 수렴할 목표가 없다 — 그래서 §10 로드맵은 이 하네스(V2-M5)를 L0로 앞당겨 가장 먼저 만든다.

7.1 픽스처 · 지표 (골든 + 홀드아웃)

대표 질의를 정답(기대값)과 함께 픽스처로 고정한다. 각 줄은 하나의 테스트 케이스다. 루프 과적합을 잡기 위해 골든셋(루프가 보고 향하는 목표)과 홀드아웃셋(루프에 미노출 — 일반화 검증)으로 split을 나눈다.

7.2 /agent/v2/eval · v1↔v2 비교

채점은 실행 없이(dry-run) analyze → plan까지만 돌려 의도·계획만 평가한다 — 실제 ERD/DB를 건드리지 않으므로 안전하고 반복 가능하다. 

# POST /agent/v2/eval  — 픽스처 일괄 채점 (실행 생략, 계획까지만)
@router.post("/eval")
async def eval_run(body: EvalBody):
    cases = load_fixtures(body.path or DEFAULT_FIXTURES)
    rows = []
    for c in cases:
        intent = analyze_only(c.query, c.context)          # analyze 노드만
        plan   = plan_only(intent) if intent.kind != "answer" else []
        rows.append(score_case(c.expect, intent, plan))    # 케이스별 채점
    return {"summary": aggregate(rows), "rows": rows}   # 스코어카드

9.디렉토리 · 배포 구조

표기 — 🟢 신규 · 🟡 수정 · ⚪ 기존(불변). v2는 agent/v2/·routers/v2/ 하위 디렉토리로 격리한다(부모와 동일 규약). 부모 패키지의 기존 v1 파일은 한 줄도 건드리지 않는다.

백엔드는 agent/v2/(중첩) · 프론트는 js/agent_v2/(형제) — 의도된 비대칭
백엔드 v1은 패키지(agent/)이므로 routers/v2/처럼 agent/v2/로 중첩한다. 반면 프론트 v1은 패키지가 아니라 평면 파일(agent_panel.js·agent_settings.js·agent_tools.js)이라 부모 js/agent/가 없다 — 여기에 맞춰 v2를 js/agent/v2/로 넣으려면 v1 파일을 이동(=수정)해야 하므로 격리 위반이다. 따라서 프론트는 v1을 건드리지 않는 형제 디렉토리 js/agent_v2/로 둔다(둘 다 "v2를 한 곳에 격리"라는 동일 원칙).
🔒 v1 파일 접촉 = 단 2곳, 모두 가법적
백엔드는 main.py의 가드 등록 1블록, 프론트는 index.html의 스크립트 로드·마크업 추가뿐이다. 두 변경 모두 기존 줄을 고치지 않고 추가만 하며, 되돌리려면 추가분만 지우면 된다. 그 외 v1 파일(routers/agent.py·agent/**·agent_panel.js·agent_settings.js·agent_tools.js)은 diff 0을 강제한다.

9.1 격리 계약 — v1 무손상 보장

v2의 어떤 추가·수정·삭제도 v1에 영향을 주지 않는다. 이것은 권고가 아니라 강제 계약이며, 아래 세 가지 불변식(invariant)으로 보장하고 마지막에 diff 화이트리스트로 검증한다.

🔁 자율 루프에서의 역할 — 매 라운드 하드 게이트
자율 개발 루프(§12~15)는 매 반복마다 코드를 자동 수정하므로, 이 격리 계약이 루프의 안전벨트가 된다. 루프는 라운드마다 ④단계에서 diff 화이트리스트(아래)가 비어 있는지와 픽스처·채점기 무변조를 검사하고, 위반 시 즉시 롤백한다(§14.2). 즉 AI가 v1을 건드리거나 테스트를 변조해 점수를 위조하는 것을 물리적으로 막는다.

불변식 ① 의존 방향은 단방향 — v1 → v2 참조 금지

그림 4 — v2가 agent/v2/로 부모 패키지 안에 들어와도, 의존은 v2 → v1(읽기 전용) 한 방향만 허용한다. 부모의 v1 모듈(agent/graph.py·agent/__init__.py 등)은 자식 agent.v2를 절대 import하지 않는다(파이썬 표준 "부모는 자식을 모른다" 규약). 따라서 agent/v2/를 통째로 삭제해도 v1은 그대로 동작한다.
규칙내용
v1 → v2 금지부모의 v1 파일(agent/__init__.py·agent/graph.py·agent/nodes/* 등)과 routers/agent.py는 agent.v2·routers.v2를 절대 import·참조하지 않는다. (있으면 격리 위반)
v2 → v1 읽기만v2는 v1의 frozen 원시모듈(키스토어·crypto·DB 어댑터·llm 팩토리·tools_proxy·db_docs·툴 카탈로그)을 import해 읽기만 한다 — 수정·몽키패치 금지.
분기 로직은 복제v2가 다르게 동작해야 하는 노드(analyze·plan·verify·graph)는 v1 import가 아니라 agent/v2/에 독립 구현. 공유는 "안 바뀌는 것"만.

불변식 ② 실패 격리 — v2가 깨져도 v1·앱이 산다

v2 라우터 등록을 가드로 감싼다. v2 패키지가 import 에러·문법 오류·삭제 상태여도 앱과 v1은 정상 기동한다.

# main.py — v1 영역은 그대로, v2만 가드 등록 (추가 블록)
app.include_router(agent.router, prefix="/agent")        # ⚪ v1 (불변)

try:                                                     # 🟢 v2 — 실패해도 앱·v1 무영향
    from routers.v2 import agent as agent_v2
    app.include_router(agent_v2.router, prefix="/agent/v2")
except Exception as e:                                    # import 실패·반쪽 삭제 등
    logging.warning("v2 agent router disabled: %s", e)   # 조용히 비활성, v1 계속

불변식 ③ 런타임 자원 분리 — 상태가 섞이지 않는다

자원분리 방법
HTTP 경로/agent/*(v1) vs /agent/v2/*(v2) — 완전 분리. v1·v2 패널이 공존해도 전역·DOM 분리로 무간섭(A/B)
그래프 인스턴스v2는 agent/v2/graph.py의 독립 compile + 독립 Checkpointer. thread_id 네임스페이스 분리(예: v2_*)
프론트 전역v2 스크립트는 _AGENT_V2_* 접두 전역만 사용 — v1의 _AGENT_URL·_agentThreadId 등 전역을 재사용·재정의하지 않음
DOMv2 패널은 별도 컨테이너(#agentV2Panel) — v1 패널 DOM·이벤트 핸들러와 겹치지 않음
공유 읽기 자원OpenAI 키스토어·AGENT_TOOL_CATALOG는 읽기 공유(상태 변경 없음) — 동시 사용해도 충돌 없음
✅ 격리 검증 — diff 화이트리스트 (수용 기준)
v2 구현 PR의 git diff --stat에서 기존 파일 변경은 정확히 다음 2개로 한정되어야 한다. 그 외 v1 파일이 한 줄이라도 바뀌면 격리 위반으로 반려.
  • proxy/python/main.py — v2 가드 등록 블록 추가만
  • index.html — agent_v2/* 스크립트 로드·v2 패널 마크업 추가만
검사: git diff main -- proxy/python/routers/agent.py ':!proxy/python/agent/v2' proxy/python/agent/ js/agent_panel.js js/agent_settings.js js/agent_tools.js 결과가 비어 있어야 한다.
⚠️ agent/v2/ 하위화의 유일한 비용 — 검사 pathspec 제외
v2가 agent/ 안에 들어오면서, "v1 패키지 전체(proxy/python/agent/) diff 0"이라는 단순 검사가 불가능해졌다(그 경로가 이제 v2 추가분을 포함). 따라서 검사에 ':!proxy/python/agent/v2' 제외 지정을 반드시 붙인다. (routers/v2/도 routers/agent.py만 콕 집어 검사하는 것과 동일한 패턴 — 부모 디렉토리 통째가 아니라 v1 파일·v1 서브트리만 대상.)
⚠️ "수정해야 하면 복제한다" 원칙
v2 작업 중 공유 frozen 모듈을 고쳐야 할 것 같으면 — 고치지 말고 agent/v2/로 해당 부분만 복제해 v2 사본을 수정한다. 공유 모듈의 시그니처·반환·부수효과를 바꾸는 변경은 v1 회귀 위험이 있으므로 전면 금지. (중복 비용 < v1 파손 위험)

승격(선택) — 격리 해제는 별도 결정

v2가 지표상 우위를 확인하면(§7) 승격한다. 이때 비로소 v1 파일을 건드린다: main.py prefix를 /agent로 전환하고 v1 디렉토리·v1 프론트를 제거한다. 승격은 격리 계약의 종료 시점이며, 그 전까지 위 불변식은 예외 없이 유지된다.

12.자율 개발 루프 — v2를 만드는 방법

§1~11은 무엇을 만들지(의도·계획·검증·하네스)를 정의했다. §12~15는 어떻게 만들지를 정의한다 — 사람이 매 수정을 지시하지 않아도, AI가 주어진 질의를 v2가 올바르게 처리할 때까지 계획 → 구현 → 검증을 스스로 반복하며 agent/v2/ 코드를 고쳐 나가는 자기수정 루프다.

🎯 핵심 원리 — 검증 오라클이 전부다
자율 루프는 오라클(자동 검증기)의 품질만큼만 똑똑하다. "올바름"이 사람 눈대중이 아니라 재현 가능한 점수로 정의되어야 루프가 멈출 지점을 안다. v2엔 이미 그 오라클의 청사진이 있다 — §7 테스트 하네스(/agent/v2/eval · fixtures.jsonl · dry-run 채점). 본 루프는 §7을 "사람이 보는 리포트"가 아니라 "AI가 향하는 손잡이"로 재사용한다. 설계의 80%는 코드 작성법이 아니라 "정확함을 어떻게 기계적으로 정의·측정하는가"다.

14.1 루프 드라이버 — 세 가지 선택지

방식구성장점 / 한계
A. Claude Code /loop + feature-dev 추천(도입) /loop가 매 반복 feature-dev 하네스를 호출. 정지 조건은 프롬프트로 명시, eval 결과를 컨텍스트로 회수 기존 자산 재사용·관측 쉬움 / 정지 판정이 모델 주도라 가드 프롬프트 견고성 필요
B. Workflow 스크립트 추천(자동화) loop-until-pass: while(통과율<목표 && rounds<max && budget){ plan→implement→gate→verify }. 점수·예산·무진전을 코드로 판정 정지/롤백/예산이 결정적·치팅 차단 강함 / 스크립트 작성 필요, 대규모 토큰은 명시적 opt-in
C. Headless claude -p + bash 외부 셸 루프가 claude -p "..." 호출 후 runner 종료코드로 분기 CI·무인 실행 적합 / 컨텍스트 연속성·관측성 약함, 직접 배관 부담
권장 경로
먼저 A로 반자동(사람이 라운드마다 눈으로 확인)으로 오라클 신뢰도를 검증한 뒤, 안정되면 B(Workflow)로 자동 loop-until-pass로 승격한다. B는 점수 상승·회귀 롤백·예산/무진전 정지를 전부 스크립트로 보장하므로 치팅·폭주에 가장 강하다. 
// (B) Workflow loop-until-pass 골격 — 개념 스케치
let best = 0, dry = 0
while (best < TARGET && rounds++ < MAX && budget.remaining() > FLOOR) {
  const card  = runEval()                       // VERIFY: 스코어카드
  const plan  = await agent(planPrompt(card))       // 가설 1개
  await agent(implementPrompt(plan))             // agent/v2/ 만 수정
  if (!gatePass()) { revert(); continue }       // v1 diff·픽스처 게이트(§9.1)
  const after = runEval()
  if (after.score > best) { best = after.score; dry = 0 }
  else { revert(); if (++dry >= K) break }       // 회귀 롤백 · 무진전 정지
}
