케이스를 17 → 119개(7배)로 확장하고 P2로 오라클을 보정한 뒤, P3 루프 2회(① act/mixed 규칙 → ② 홀드아웃 비공개 잔여 공략)가 prompts.py만 고쳐 골든 통과율 86.7% → 99.2%, 홀드아웃 97.7% → 99.6%로 끌어올렸다(reps=5 독립 재현). 목표(0.90/0.90) 초과 달성 · v1 무손상 · 하드코딩 없는 일반화 · 홀드아웃 비공개 가드로 leakage 없이 검증.

1.개요 · 결과 요약

1차 최적화는 17개 픽스처로 기본 분류 결함을 잡았다. 2차는 "에이전트스러운" 복잡 질의(다중 목표·교차 scope·역공학·관계 편집 등) 119개로 잣대를 크게 넓혀, 더 미묘한 의도 분석 결함을 드러내고 자동으로 수렴시키는 것이 목적이다.

2.작업 워크플로우

docs/ref.md 지시 순서를 그대로 따랐다.

새 브랜치 → 가상 카탈로그 보강 → 복잡 케이스 100+ 추가 → P2(오라클 검증·보정, 반복) → P3(loop-until-pass, 프롬프트·노드 수정 허용) → 최종 보고서
핵심 원칙 — 구조는 사람이, 품질은 루프가
카탈로그·케이스·오라클 보정 같은 잣대(구조)는 사람이 세우고, 의도 분류 정확도 같은 품질은 eval 점수를 향해 루프가 자동 수렴시킨다. P2(오라클 신뢰도)가 P3(자동화)의 전제다.

3.가상 카탈로그 보강

복잡한 에이전트 동작을 검증하려면 더 풍부한 도구 어휘가 필요하다. 의도/계획 품질 평가용 가상 카탈로그(runner.DEFAULT_CLIENT_CATALOG)에 3개 툴을 추가했다.

5.P2 오라클 검증·보정

루프를 켜기 전, 채점기 판정이 사람 눈에도 맞는지 직접 검수하고 거짓 실패(픽스처 오류)를 교정했다. 이 보정이 자동화의 전제다.

6.P3 자동 최적화 루프

오라클을 잣대로 driver B(Workflow loop-until-pass)를 가동했다. 매 라운드 VERIFY → PLAN(가설1) → IMPLEMENT → GATE → RE-VERIFY, 점수↑면 채택·↓면 롤백.

항목값
결과success — 1라운드

게이트PASS (v1 무손상·테스트자산 동결)
점수 (reps=3, 루프 측정)golden 0.889 → 0.938 · holdout 0.992 → 1.000

6.1 프롬프트 변경 — act/mixed 규칙 정교화

P2가 드러낸 핵심 결함: 모델이 순수 다중 쓰기('세 테이블 생성', '둘 다 삭제')와 순수 다중 읽기('위반 찾아 구조 보여줘')를 mixed로 과분류했다(C-02·D-04·F-02·A-02·A-08·A-09·A-10 클러스터). 루프는 ANALYZE_SYSTEM을 다음 원리로 수정했다.

# 핵심 변경 (요지)
act : 목표가 여러 개라도 전부 쓰기면 act · 전부 읽기여도 act.
mixed : 사용자가 명시적으로 요청한 읽기 목표 AND 쓰기 목표가
        함께 있을 때만. 쓰기 수행용 내부 사전확인은 읽기 목표가 아니다.
치팅 점검
질의→정답 하드코딩·픽스처별 특수분기 없음. 분류 원리를 일반화한 수정이며, 홀드아웃 100% 달성이 일반화(과적합 아님)를 입증한다.

6.2 홀드아웃 비공개 잔여 공략 (Run B)

Run A 후 잔여 5건(R-02·Q-09·M-05·L-06·A-08, 모두 골든)을 마저 잡기 위해 하네스를 강화해 한 번 더 돌렸다.

강화점내용
홀드아웃 비공개 true holdout최적화 에이전트는 --split golden만 실행 — 홀드아웃을 보지도·겨냥하지도 못함. 별도 읽기전용 에이전트가 홀드아웃을 검사만 한다(개선에 미사용)
과적합 가드커밋 후 홀드아웃 검사 → holdout<0.95면 git reset으로 그 커밋 롤백
loop-until-dry임계 추측 없이 — 골든 오르는 한 계속, 무진전 K=3회면 종료

잔여 5건을 정조준한 프롬프트 규칙을 추가했다(2커밋).

# clarify (ANALYZE)
'저 테이블들/그것들' 복수 지시어 → clarify · '설명해줘'가 특정 테이블이면 act (개념 아님)
# 읽기 툴 (PLAN)
'DDL 뽑아' → generate_ddl · '정규화 위반 찾아' → normalize_check · 다중 읽기는 스텝 분리
# 관계 툴 (PLAN)
'연결/잇다/만들어' → create_relation · 기존 '관계를 …로 바꿔' → set_cardinality (지웠다 다시 만들지 말 것)
⚠️ 하네스 노트 — 루프 제어 크래시(작업은 보존)
Run B의 Workflow는 후속 라운드 에이전트가 구조화 출력(StructuredOutput)을 호출하지 않아 제어 흐름이 중단됐다. 그러나 그 이전 라운드의 커밋된 프롬프트 개선 2건은 정상 보존됐고(working tree 깨끗·게이트 PASS), 아래 독립 검증으로 결과를 확정했다. (개선점: 대량 작업 에이전트의 스키마 반환 강제·라운드당 작업 축소.)
✅ Run B 결과
골든 94.1% → 99.2% · 홀드아웃 99.6% 유지. 홀드아웃을 한 번도 보지 않고 고쳤는데도 유지된 것은 leakage 없는 진짜 일반화의 증거다.

8.잔여 표적

Run B로 1차 잔여 5건(R-02·Q-09·L-06·A-08 통과, M-05 0→0.8)은 사실상 해소됐다. reps=5 기준 남은 미통과는 3건뿐이며 모두 흔들림(0.6~0.8)으로, 하드 실패는 0이다.

ID질의통과율증상
M-05회원 DDL 뽑아보고 컬럼 추가80%mixed — generate_ddl/add_attribute 조합 가끔 흔들림
M-06실제 DB users 조회 뒤 status 컬럼 추가80%mixed(db) — fetch+run_sql 조합 가끔 흔들림
M-07상품 구조 확인하고 가격 컬럼 타입 수정60%mixed — describe+update_attribute 조합 흔들림

모두 mixed(읽기+쓰기) 케이스의 툴 조합 비결정성이다. golden 99.2%로 목표를 크게 초과해 추가 최적화의 한계효용은 낮다. 필요시 reps↑ 안정화 또는 동일 루프 재실행으로 처리(런북 agent/v2/eval/README.md).

케이스를 7배로 늘렸는데도 1라운드·단일 프롬프트 수정으로 목표를 넘었다. 1차에서 세운 분류 원리가 견고해, 2차는 그 위에 다중목표 분류라는 한 겹만 보강하면 됐다. 누적된 프롬프트가 점점 일반화 성능을 높이고 있음을 시사한다.

10.결론

  • 목표 달성 — 119개 복잡 케이스에서 골든 99.2% / 홀드아웃 99.6%(reps=5), 목표 0.90/0.90 크게 초과.
  • 안전 보장 — v1 무손상(diff ∅·grep 0)·테스트자산 동결·하드코딩 없는 일반화를 게이트와 독립 검증으로 확인.
  • 홀드아웃 비공개 검증 — Run B는 루프가 홀드아웃을 한 번도 보지 않고 고쳤는데 홀드아웃 99.6% 유지 → leakage 없는 진짜 일반화 입증.
  • 잔여 — 3건(M-05·M-06·M-07)뿐이며 모두 mixed 케이스의 툴 조합 흔들림(0.6~0.8)·하드 실패 0.
  • 재현 — 새 케이스 추가 후 agent/v2/eval/README.md의 단계별 런북으로 동일 절차를 반복할 수 있다.

본 보고서는 2차 자동 최적화의 실행 기록이다. 채택 변경은 feature/agentv2-autoloop-2 브랜치의 d4e2295(agent/v2/common/prompts.py)이며, 게이트·격리·치팅 점검·reps=5 재현을 모두 통과했다. 잣대(픽스처·오라클)는 agent/v2/eval/에, 자동 루프는 docs/plan/agentv2_autoloop.workflow.js에 있다.
